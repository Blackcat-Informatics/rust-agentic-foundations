## Choices

* `module_named` finds the crate path by growing prefixes (as `resolve_in`); a module
  path that two crates hold is `Ambiguous` between the module items. `Heads::Use { test:
  false }` is kept for `resolve_from`: a test target's prelude already names its
  dev-dependencies `everywhere`.
* `ImplBlock` records are built in `attach_impls`/`attach_unresolved`, charged
  (`vec_slot::<ImplBlock>()` + interned self type and trait + the two id lists) at the
  `impl` line, sorted in `finish` and numbered there (`ImplId` = position).
* Reachability: no new `Budget`. The work is linear in tokens and runs (each file
  lexed once, runs placed in one sweep, a run resolved once per module and test flag,
  its prefixes in one incremental walk through the refactored `Index::step`), and the
  tokens are already bounded by the load's token and byte budgets, so a hostile input
  cannot make it super-linear; the 50,000-segment fixture pins that a prefix-by-prefix
  walk would pass the ceiling.
* Runs are read as code (`Heads::Code`), not as `use` paths: no viewer visibility, and
  in 2015 from the module. A prefix counts when the walk would make the resolver answer
  with one symbol: an undecided import, a broken glob read or several symbols name
  nothing (fixture with a broken glob and an ambiguous glob pair).
* Scanner: a single `.`, a `'`, a `$` other than `$crate`, the name after a declaring
  keyword (`fn struct enum union trait type mod const static`, `macro_rules!`), a
  one-segment run before a single `:` and a run after `>::` are no paths; keywords end
  runs; raw identifiers are never keywords. Lexing runs on a scoped thread with
  `PARSE_STACK_BYTES` so proc_macro2's thread-local span map dies with it.
* Module semantics follow workplan-strict rule 3: a module opens only as a root or by
  contains from an opened module; its own tokens are its header; module-level `use`,
  `const _` and macro invocations belong to no item. `#[macro_export]` macros are read
  from the crate root. Trait members are read from their trait's module, block members
  from their block's module.
* `cap:source-index#constraints` and `#verification` were added to the change record's
  `affects` (both sections now state T5).

### Design and choices

* `raf-okf`: `DocType::Debt` (directory `work/debt`, prefix `debt:`, singleton `debt:default`, a record), keys `type`, `id`, optional `tags`/`timestamp`, `findings` (rows of exactly `kind`, `subject`), `lines` (rows of exactly `item`, `orphans`). Existing rules judge the rows (`okf-row-unknown-key`, `okf-row-missing-key`, `okf-duplicate-entry`, `okf-bad-measure` for an `orphans` that is not a whole number, `okf-body-not-empty`, `okf-singleton-id`); no new rule. `DebtRecord::new` sorts the rows and the writer emits them in record order, so equal debts write equal bytes. "Rows sorted" is a property of the writer and not a rule of the reader (a rule would be a new `okf-*` kind with fixtures in five places for a file a tool writes); a hand-ordered record reads fine and the next write sorts it. The fix text of `okf-singleton-id` is made from the type of the rule (`name the record `debt:default` at work/debt/default.md`), the text for coverage is byte-identical.
* `raf-workplan::debt` (new public module): `DEBT_KINDS` (ten kinds a `findings` row can hold), `DebtWrite` (path, `DebtChange` Created/Replaced/Unchanged, row counts), `DebtError` (`Open`, `NotStrict`, `Findings`, `Growth`, `Record`), `Gate::write_debt`, `Gate::record_options`, `Opened::write_debt(&RecordOptions)`, `Workplan::debt()`.
* `strict::owed` is the sole producer of the findings a row can hold: each carries its `Key` (kind and subject) from the place that raises it, so the ratchet never reads message text. `coverage-surface-unreadable` is raised by it as a finding no row can hold (an error, not debt), as are the line-walk errors.
* Line debt (Rev 2 A4): a `lines` row is `item` and `orphans`; a count only. The debt is kept per item for packages over a ceiling. A package over a ceiling that has a row for one of its items is judged by its rows (item above its row, or with no row: `coverage-lines-over-ceiling` at `lines` naming the row; item below: `debt-resolved`); a package over a ceiling with no row is judged by its ceilings, as without a record; a row of a gone item or of a package within its ceilings is `debt-resolved`. This keeps one invariant: the record always equals the present debt, so the write never records growth silently (a reading in which rows only excuse lines from the ceiling would let a new item under a raised ceiling pass unrecorded and then be written in). The Contract of `cap:workplan-strict` says so.
* Subjects: claim key (`strict-claim-uncovered`), `cap:<slug>` (`strict-example-missing`), `cap:<slug>#<section>` of the section the rule judges (`strict-matrix-missing` Verification, `strict-usage-unbound` Usage, `strict-limitations-missing` Constraints, `strict-claim-unit-collapsed` Contract, `strict-section-thin` any), the reported path of the item or test for the three coverage kinds.
* The write: `NotStrict`; `Findings` while a default finding, an unreadable surface, a report that cannot count the lines or a stale generated block stands; `Growth` when a record exists and a present finding, an item above its row, an item with no row or a package newly over a ceiling is not held; otherwise create (adoption) or replace; an equal record is left untouched. Only `work/debt/default.md` is written; a record's own SPDX lines are kept when none are given. The keys carry no version, so only the adoption case records growth (`arch:debt-ratchet` says so).
* The CLI: `debt --write` (required), `--copyright`/`--licence` as the other writers; `-q` hides the written outcome and keeps the findings that stop the write; exit 0 written/unchanged, 1 findings printed and nothing written, 2 not strict (unless `--strict`), usage, unopenable, unwritable.
* `CrateLines::debt()` and the Debt column are wired: for each item of a package with orphan lines and a row, the fewer of its lines and its row, summed (0 without a record or a row).
