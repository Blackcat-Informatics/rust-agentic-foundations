# Plan enhancement review

Reviewed plan: `.stage/raf-workplan-model-documents-check/plan.md`
Inputs read: `issue-analysis.md`, `prior-art-assessment.md`, `issue.md`, the ten `docs/capabilities/workplan-*.md`, `docs/architecture/okf-profile.md`, `tests/docs_contract.rs`, `tests/support/mod.rs`, the public APIs of `raf-okf` and `raf-source`, `Makefile`, `.githooks/pre-commit`, `AGENTS.md`. Standing constraints: no `.goals` file; `AGENTS.md` rules apply (fail hard, every rule has a negative fixture, no deferrals, Rust first).

The plan is sound on scope and on the J1 consolidation. What it under-asks is the *shape* of the crate: it is laid out as five parallel modules (`graph.rs`, `bindings.rs`, `generated.rs`, `status.rs`, Gate) each reading the documents its own way, when the domain's definitive structure is one semantic graph with rules as integrity constraints and every output (check, sync, status, and the next issues' impact, reconcile, preview, coverage) as a query or materialised view over it. The user has a real consumer waiting; the items below are ordered by how much they change what that consumer receives.

## TRANSFORMATION

1. **TRANSFORMATION. One semantic graph; rules are integrity constraints; generated blocks, `status` and the lifecycle commands are views over it.** Cost **M** (a structuring decision, little extra code). Payoff: decisive. The document-model Contract already says the graph "supports questions in both directions: which code realises this capability, which capability explains this symbol, which tests address this guarantee, and which sections this change must update". Every later workplan capability is a graph query plus a node kind: `change impact` (reconcile) = `changes` + `affects` + bindings + dependants + sections that link to the affected sections; `docs preview` (cli) = apply proposal nodes to a copy; two-way coverage = unbound item and unbound test nodes; current rationale = architecture nodes with no inbound link edge; evidence/claims = a new node kind and edge; prose assessment = a digest over a section node and its bound items. If the plan builds the graph as one module among five, each later issue rediscovers the relations in its own code. Where it changes the plan: Task 2 ("`graph.rs` has nodes for ... and edges for ... It has queries in both directions"), Task 5 (`generated.rs`), Task 6 (`status.rs`), and J13 (`Workplan::sync() -> SyncReport`). **REWRITE TO:** "`Workplan::load` builds the `Graph` once (nodes: capability, section, change, proposal, generated block, symbol, test, example, architecture page, linked path; edges: binds, depends, affects, proposes, links-from-section-to-target, dependant-of). `check()` runs every `Rule` as a predicate over the graph. `sync()` renders each `View` kind (`verification-matrix`, `relationships`, `catalogue`) as a pure function of the graph and splices it; staleness is `render(view) != current content`. `status()` is the `catalogue` projection without the Markdown. The graph exposes typed queries: `realises(cap)`, `explains(symbol)`, `addresses(cap)`, `must_update(change) -> Impact`, `dependants(cap)`, `linkers(section)`, `unbound_shipping_items()`, `unbound_tests()`. Each query has a fixture asserting its answer on the graph fixture of R12." The acceptance row for R12 then reads "`Workplan::graph()` answers each query above", not just "exposes the nodes".

2. **TRANSFORMATION. One `Finding` vocabulary with stable kinds and a fix hint, shared by `check` now and by obligations next.** Cost **S–M**. Payoff: `AGENTS.md` demands "an error with a message that says how to fix it"; the reconcile Contract's obligation table has an "Evidence that resolves it" column; the CLI Contract's JSON output is `kind`, `path`, `section`, `message`. The plan's `Violation { file, line, rule }` (Task 1) has no section, no stable kind id and no fix text, so the CLI and reconcile issues will each wrap it. Where: Task 1 "Every raf-okf violation becomes a `Violation { file, line, rule }`" and Task 7 "`assert_clean` panics with a report listing every violation (file, line, rule)". **REWRITE TO:** "A `Finding { path, at: raf_okf::Location, rule: Rule }` where `Rule` is `Profile(raf_okf::Rule)` or one of the crate's cross-document rules; every `Rule` has `kind() -> &'static str` (kebab, stable, documented in the capability's Contract as the violation vocabulary), `Display` for the message, and `fix() -> &'static str` saying what resolves it. `check()` returns findings sorted by (path, location, kind) and deduplicated; `assert_clean` prints `path:line  kind  message  (fix)`. The R26 coverage test matches exhaustively over the crate's `Rule` so a kind without a fixture and a fix text fails to compile." Note that `raf_okf::Rule` and `Location` are `#[non_exhaustive]`, so the exhaustive-match coverage test covers the crate's own rules and a separate test asserts every raf-okf rule kind the fixtures produce surfaces through `check` (the plan's J10 already promises this).

3. **TRANSFORMATION. Section-granular link edges, so "which sections link here" is answerable.** Cost **S** (raf-okf gives `Link::line()` and `Body::sections()` with byte spans; the mapping is a range lookup). Payoff: the reconcile Contract's `change impact` prints "the sections that link to the affected sections, because those readers are affected too", and `affects` is already section-granular. A graph whose link edges run document-to-document cannot answer it and would have to be rebuilt. Where: Task 2 "edges for bindings, depends, affects and links". **REWRITE TO:** "A link edge runs from the section node that holds the link (or the document node when the link is above the first `##`) to the target path node or, when the target carries an anchor, the heading node it names. A fixture asserts `linkers(cap:beta#contract)` returns `cap:alpha#explanation` for a link in alpha's Explanation to `./beta.md#contract`."

## LEVERAGE

4. **LEVERAGE. `impact` and `preview` are in-scope graph functions; deliver them in the library now.** Cost **S** once item 1 and 3 exist. Payoff: the CLI Constraint says "The binary holds no logic of its own", so `Workplan::impact(change) -> Impact` and `Workplan::preview(change) -> String` must live in `raf-workplan` regardless; building them beside the graph they query costs almost nothing, and the consumer gets "what does this change touch" and "how will the doc read" as library calls before `cargo-workplan` exists. `preview` is a text transform: for each `ProposedBlock` of the named change, drop the marker line and the `> ` prefixes; markers of other changes stay. Where: "Enhancements considered and declined" and Task 2. **REWRITE TO:** add to Task 2: "`impact(change)` returns the capabilities in `changes`, the sections in `affects`, their bindings, the dependants, and the linking sections (item 3); `preview(change)` returns each listed capability's text with that change's PROPOSED blocks folded in and the markers removed, and never writes. Fixtures: an impact fixture asserting each list, and a preview fixture asserting the markers are absent, the proposed text present, and a second change's block untouched." Record both as claims on `change:workplan-document-model` so the outcome is tracked.

5. **LEVERAGE. `status` and the `catalogue` block are one projection.** Cost **S**. Payoff: the CLI and the index can never disagree about a gap. Where: Task 5 "`catalogue`: state groups in order, slug order, gaps for `implementing`" and Task 6 "`status.rs`". **REWRITE TO:** "`Roadmap` (Task 6) is computed once from the graph: groups in the Contract's order, rows with slug, title, description, open changes and gaps (empty list, unresolved binding). The `catalogue` view renders a `Roadmap`; `status()` returns it. One fixture asserts the catalogue rows equal the roadmap rows."

6. **LEVERAGE. Reuse the precedent's whole fixture set and its `Repo` shape through `MemoryTree`.** Cost **S**. Payoff: `tests/docs_contract.rs` already has ~120 named negative fixtures (lines 1060–3600) and a `fixtures::valid()` builder; the plan says "its existing fixtures for model rules move into `crates/raf-workplan/tests`" (J1) but the tasks describe writing fixtures afresh. **REWRITE TO:** in Task 1: "Port `fixtures::capability`, `fixtures::valid` and the `assert_hit`/`assert_cases` helpers into `crates/raf-workplan/tests/support`, backed by `MemoryTree`; each ported test keeps its name so the diff shows the move. The split-link, placeholder and symlink tests that are repository policy stay in `docs_contract`."

7. **LEVERAGE. Make the source roots explicit and keep the precedent's.** Cost **S**. Payoff: `docs_contract` loads `Workspace::load(..., &["crates"])`; J12 says `Gate::workspace` uses roots `["."]`, which also discovers the root package (good: `tests/docs_contract.rs` tests become bindable) and the `fuzz/` workspace (its own `Cargo.toml`, separate lints), which a consumer may not want and which can fail discovery. Where: J12 "the workspace sources rooted there (raf-source roots `["."]`)". **REWRITE TO:** "`Gate::workspace(dir)` uses roots `["."]` by default and offers `.source_roots(&[..])`; this repository passes `["crates", "."]`-equivalent coverage only if the fuzz workspace loads cleanly, otherwise `["crates"]` plus the root package explicitly. A fixture asserts a root list that finds no package is an error (raf-source `NoRoots`), never an empty index."

## UTILITY

8. **UTILITY. Expose the two-way coverage queries now, as queries not rules.** Cost **S** (raf-source gives `items()` with `visibility`, `is_shipping`, `doc_hidden`, and `test_fns()`). Payoff: the consumer sees undocumented public surface and unbound tests on day one; `cap:workplan-two-way-coverage` later promotes the queries to rules and adds the exclusion file. Where: Task 2 (item 1's query list). **REWRITE TO:** "`unbound_shipping_items()` lists `pub` items of shipping targets that no `bindings.code` entry resolves to (re-exports count as bound); `unbound_tests()` lists `#[test]` functions no `bindings.tests` entry resolves to. Neither is a `check` rule. Fixture: one bound and one unbound item; a private item is absent." Not a deferral: the considered capability's PROPOSED Contract is unchanged, and the query is part of the document-model's "questions in both directions".

9. **UTILITY. The `docs_sync` example takes a root path.** Cost **S**. Payoff: a consumer can run `cargo run -p raf-workplan --example docs_sync -- /path/to/repo` on their repository before `cargo-workplan` exists, which is the first tool they can give feedback on. Where: J13 "`crates/raf-workplan/examples/docs_sync.rs` ... lets this repository write its blocks" and Task 5. **REWRITE TO:** "The example takes an optional root argument (default `.`), prints each file it rewrote, exits 0 when nothing changed and 1 when it wrote, so `make docs-sync` and a consumer's CI can both use it."

10. **UTILITY. Generalise the Usage/Examples doctest pairing.** Cost **M**. Payoff: `docs_contract` lines 3262–3287 pin that the `rust` blocks under Usage and Examples of `okf-profile.md` and `source-index.md` equal the leading crate doctests, which is what makes a capability's Usage compile. That is a general rule any consumer wants, keyed naturally by an `examples` binding to the crate root (`raf_okf`). Where: J1 keeps it as repository policy. **REWRITE TO (optional):** "An `examples` binding to a crate-root path pairs the capability's Usage and Examples `rust` blocks with that crate's leading `//!` doctests; a mismatch is a `usage-doctest-mismatch` finding naming the block and line. `DOCTEST_PAIRS` then leaves `docs_contract`." If declined, say so with the reason (for example that doctest pairing is a repository convention and not part of the profile).

## ROBUSTNESS

11. **ROBUSTNESS. `Tree` is read-only; sync needs a contained, two-phase write seam.** Cost **S–M**. `raf_source::Tree` has `read`, `list`, `entry` only (`tree/mod.rs` 146–219). The plan says "`Workplan::sync()` ... writes through the tree" (J13) and "writes through `DiskTree`" (Task 5), which does not exist. Also `replace_spans` is transactional per document, not across files, so an error on the fifth file leaves four written. **REWRITE TO:** "`sync()` returns `SyncReport { edits: Vec<(RelPath, String)> }` computed for every file before anything is written, over the same loaded document set, and refuses with no write if any view fails to render. `Workplan::apply(report, root)` writes each path only when it was loaded through the tree (or is the new `docs/capabilities/index.md`), by writing a sibling temp file and renaming. Fixtures: an unknown-kind block in the second file leaves the first unwritten; `apply` to a path that was not loaded is refused."

12. **ROBUSTNESS. The created `index.md` must carry its SPDX header, and the first sync must pass `reuse`.** Cost **S**. The profile says "apart from its SPDX comment, every non-blank line lies inside a generated block", `AGENTS.md` says every `*.md` is CC-BY-4.0 with the two HTML-comment lines, and `make reuse` fails otherwise. J7 says "created by the first sync, with no frontmatter and only a `catalogue` block". **REWRITE TO:** "The first sync writes the two SPDX HTML-comment lines (copyright text taken from a `SyncOptions` field; refused when unset), a blank line, then the `catalogue` block. A fixture parses the result with `raf_okf::Index::parse` and asserts `is_capability_index`; the repository gate run after Task 8 includes `make reuse`."

13. **ROBUSTNESS. An empty or wrong-rooted repository must not pass `assert_clean`.** Cost **S**. The Usage shows `Gate::workspace(env!("CARGO_MANIFEST_DIR"))`; in a consumer's member crate that is the crate directory, not the workspace root, so `docs/` is absent and a Gate that loads zero documents reports zero findings: a false green. The precedent guards against this (`docs_contract.rs` 920–926 requires at least one document of each type; 934–938 requires known symbols). **REWRITE TO (Task 7):** "`Gate::workspace(dir)` is an error when `docs/capabilities` does not exist under `dir`, and `check` on a tree with no capability document is a finding (`no-capabilities`). A missing `work/changes` or `docs/architecture` directory is an empty set, not an error, so a consumer with no open change passes. Fixtures: an empty tempdir panics with the message naming the missing directory; a tree with `docs/capabilities/` but no `work/` passes."

14. **ROBUSTNESS. Define the link universe: tracked paths, on-disk files, and symlinks.** Cost **S–M**. The profile rule is "looked up in the list of tracked paths (the Git index), and a link whose target is a tracked symlink is a violation". The precedent takes the universe from `git ls-files` (`tests/support/mod.rs`) and the hook judges a checkout of the index. J6 says links "resolve to existing repository paths", which with `DiskTree` means on-disk files: a link to an untracked file passes in `cargo test` and fails in the hook, and `DiskTree` cannot see a symlink by `entry()` once it is followed (`EntryKind::Symlink` exists but containment accepts an in-root link). **REWRITE TO (Task 3):** "`LoadOptions::paths(Vec<RelPath>)` sets the universe of link targets; absent, it is the tree listing. `docs_contract` passes the index listing from `tests/support`, so the gate and the hook agree. A target whose `entry()` is `Symlink` is a finding. Fixtures: a link to a path outside the universe is broken although the file is on disk; a link to a symlink is refused beside one to its target."

15. **ROBUSTNESS. Specify how a doc-test `examples` binding is recognised.** Cost **M**. J5 says an example binding may resolve to "an item whose documentation holds a Rust code block", but `raf_source::Item` carries only `documented: bool` and `doc_hidden`, not the doc text. The plan does not say where the code block is read. The completion gate later refuses `no_run` and `compile_fail` doc tests, so `check` should agree. **REWRITE TO (Task 4):** "For a documented item, the crate reads the item's span from `Workspace::source(file)` and parses its `#[doc]` attributes with the re-exported `syn`; the binding resolves when a fenced block's info string is one rustdoc runs (empty, `rust`, or attributes none of which is `ignore`, `no_run`, `compile_fail`, `text` or a non-Rust language). Fixtures: a doc block that runs resolves; no block, an `ignore` block and a `no_run` block each fail naming the binding and the reason." If this belongs in raf-source as a fact (`doc_tests: Vec<DocTest>`), say so and add the changelog entry.

16. **ROBUSTNESS. Make the verification-matrix "section substantiated" rule deterministic.** Cost **S**. Task 5 says "The section is the Verification section, unless a binding is named in another section's text", which leaves open a binding named in two sections, named only in a code span versus prose, or named inside a PROPOSED block. **REWRITE TO:** "A binding substantiates every section (other than Verification) whose prose outside fences and outside PROPOSED blocks contains the bound path in a code span; when there is none it substantiates Verification; several are listed in document order in one cell. Fixture: a test named in Contract and Constraints yields `Contract, Constraints`; one named only in a fence yields `Verification`."

17. **ROBUSTNESS. CRLF documents and sync.** Cost **S**. The Contract fixes `\n` output; the profile keeps the body byte for byte and allows a CRLF frontmatter. A CRLF document would gain mixed endings on sync, and staleness would then flap. **REWRITE TO (Task 5):** "A document whose body holds `\r\n` is refused by `sync` and reported by `check` (`crlf-document`), with the fix text 'convert to LF'. Fixture: one CRLF capability beside an LF one."

## Verdict

Items 1–3 change the crate's shape and are cheapest before Task 2 is written; items 11–15 are gaps that would surface as defects in Task 5, Task 7 or at the consumer. Items 4–10 are small given 1–3.

VERDICT: NEEDS-REVISION
