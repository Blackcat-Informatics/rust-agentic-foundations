## 1. Precedent fit

### Held or improved relative to the templates (no action)
- `ci.yaml`: every action is SHA-pinned (the same SHAs as purrdf for checkout and the toolchain), `permissions: contents: read` (line 11), `persist-credentials: false` on every checkout, and a timeout on every job. The msrv job sets `RUSTUP_TOOLCHAIN=1.98.1` at job level and asserts `rustc --version`. This is the fix purrdf made in commit 94f9b0b84, where the msrv job had silently measured the repo pin for a long time. The branch's msrv is stricter than purrdf's: it uses `--all-targets`, and `make msrv` asserts the version too.
- `.githooks/pre-commit` keeps purrdf's essential safety property: it runs on a `git checkout-index` snapshot of the index (lines 16-18) and judges a partial staging as it will be recorded. It reads `issue-refs` through `git grep --cached`. It does not skip on a missing tool, because the Makefile targets hard-fail.
- `.gitignore` uses `/target` with no trailing slash, so it matches a symlinked target. This is the lesson recorded in purrdf's `.gitignore`.
- `Cargo.toml` lints are logit-loom's set plus `unused_qualifications` and `allow_attributes_without_reason`, with a reason comment on each allow. This is a justified superset. `clippy.toml` and `rustfmt.toml` match the templates. `rust-toolchain.toml` matches (floating nightly), and the floating-versus-dated choice is the one purrdf settled on after its 94f9b0b84 pin was reversed.
- Legal and community docs are purrdf's with renames and purrdf-only text removed. CoC differs by 4 lines, issue and PR templates by name only, and the SECURITY attack-surface section is rewritten for RAF. The SPDX licence of `*.md` differs (CC-BY-4.0), which is plan decision A13, not a regression.

### Divergences

**F1 — MEDIUM — `cliff.toml` is the pre-fix purrdf template; it will repeat two defects purrdf already fixed.**
- `cliff.toml:29` marks a bullet BREAKING from a per-commit `commit.breaking` and does no per-release dedup.
- purrdf's fixes are 446c23318 (deduplicate generated changelog entries) and 38b0a1da9 (mark a breaking release when the squash duplicates a subject). The reason, recorded in purrdf's `cliff.toml` header, is that a squash merge keeps the branch commit `feat(x)!: Y` beside `feat(x): Y`. After the PR-number strip they reduce to the same scope/message pair, and the non-breaking one survives. A BREAKING marker is then silently lost on exactly the release that needs it, and bullets are duplicated.
- RAF merges through `ghprsq` and uses a squash merge (stage 3). It states "a breaking change bumps the minor version" in CHANGELOG and CONTRIBUTING, so a silent loss defeats that rule.
- `cliff.toml:49-54` also lacks purrdf's `\(\s*\)` cleanup, so an input such as `(fixes #3, #4)` can leave a stray `(,)`/`()` artifact in a bullet. By inspection only; the branch's preprocessor was tested only with a PR-number strip (validation.md T4).
- Fix: port purrdf's `set_global breaking_keys` / `rendered_entries` body and the `\(\s*\)` preprocessor. This is cheap now and costly after the first tagged release.

**F2 — MEDIUM — The `issue-refs` gate false-positives on `#<digits>` shapes that purrdf learned to spare, and the Makefile gate and the Rust contract test own the same job twice.**
- `Makefile:66-75` uses `#[0-9]{1,5}\b`. A probe shows it hits `fill="#000"`, `fill="#333"` and the XML character reference `&#38;`. purrdf had to ship abc1e35c5 ("an XML character reference is not an issue reference") for the same class. No tracked file hits today (verified with `git grep`), so the gate passes, but the first SVG edit with a short hex colour or an entity fails `make check`, the hook and CI, with a message that blames the author for an "issue token".
- `tests/docs_contract.rs:380-390` implements the same rule in Rust (`1..=5` digits, not followed by a word character) and has the identical hole. Its negative fixture `issue_token_scan_spares_hex_colours` uses 6-digit colours only, so it does not cover the failure.
- The two implementations differ in scope. The test scans only `*.md` at the top level and under `docs/` and `work/` (`is_scanned`, lines 450-457). The Makefile scans every tracked text file. The pattern families are hand-copied twice (Makefile 67-72 and test lines 58-63 plus `plan_possessive`/`acceptance_label`/`pull_request_number`). That is two homes for one job, in the repository whose purpose is to remove that. Drift between them is already visible: `PR ?#?[0-9]+` in the Makefile is not word-bounded on the left (`\bPR` is, but only in the first grep), while the Rust version is.
- Families purrdf added after real escapes are absent from both: `the issue`/`the issue's`/`issue-author`, `EPIC`, `on origin/main`, and hazard labels (`F6:`). They are not in the R36 grep that the plan fixed, so this is a hardening note, not a plan violation.
- Fix: require a non-word, non-`&` prefix (`(^|[^&0-9A-Za-z#])#[0-9]{1,5}\b`, with colours of 3/4/6/8 hex digits explicitly spared), add a fixture for `&#38;` and `#000`, and let the Makefile target call one implementation. The self-gate issue is the natural place for the single home; until then record the duplication in the test header.

**F3 — MEDIUM — The CI `deny` job installs `cargo-deny` unpinned, from source, on every run.**
- `ci.yaml:94-95` runs `cargo install --locked cargo-deny`. The version floats on whatever is current, so the verdict can change with no repo change. Every other tool in the repo is pinned (`reuse@6.2.0`, actions by SHA, `rust-validate 1.98.1`). purrdf and visual-hashing do not run cargo-deny through an unpinned install; purrdf pins its tools (git-cliff, binaryen, mdbook-i18n-helpers) in the Makefile with a hard-fail version check, which is the house pattern.
- The local gate is `cargo deny --offline check` against whatever advisory snapshot is cached (`Makefile:36-38`), so a local pass and a CI result are two different checks. That asymmetry is plan decision A14; the finding is only that the tool version is not pinned on either side.
- Fix: `cargo install --locked cargo-deny@<ver>` (or a SHA-pinned install action) and record the same version in the Makefile `deny` comment.

**F4 — LOW — CI has no `concurrency` group.** purrdf has had it since 2eaac5f57: a newer push cancels the superseded run on a PR and never cancels `main`. Without it, a PR force-push queues a second full run of 8 jobs. Add the same block.

**F5 — LOW — No `pre-merge-commit` hook.** purrdf ships `.githooks/pre-merge-commit` which `exec`s `pre-commit`, so a merge git commits by itself is gated. The branch's `make hooks` sets `core.hooksPath=.githooks` (`Makefile:94`) but only `pre-commit` exists, so auto-merge commits (for example `git merge origin/main` with no conflicts, which stage 3's behind-base handling uses) skip the fast gates. The CI gates still cover them. Add the 3-line file. Also, purrdf's hook exits 0 when nothing is staged; the branch's hook runs the gates on message-only amends (harmless, slower).

**F6 — LOW — `make fmt` is check-only.** `Makefile:22` makes `fmt` run `cargo fmt --all --check`. In purrdf and logit-loom `make fmt` formats. A contributor typing `make fmt` after a hook refusal gets another failure instead of a fix. The plan fixed the target name, so either add a `fmt-fix`/`fix` target or rename to `fmt-check`. Also, `$(MAKE)` recursion inside `check` has no `--no-print-directory` (purrdf sets `MAKEFLAGS += --no-print-directory`), so `make check` prints `Entering directory` banners. Cosmetic.

**F7 — LOW — Version agreement is asserted in prose with no gate.** `AGENTS.md:202-203` says `CITATION.cff` and `[workspace.package]` "carry the same version". Both say `0.1.0` today, but nothing checks it (`rg` finds no version rule in the Makefile or `docs_contract.rs`). purrdf has `check-versions.py`. This breaks the branch's own principle "every rule has a negative fixture" (`AGENTS.md:138-146`). `CITATION.cff` also names version `0.1.0` and has no `date-released`, `url` or author-person entry, which purrdf's has. A citation of an unreleased version is acceptable, but a version-agreement check should land with it, not at the first release.

**F8 — LOW — `deny.toml` lacks per-entry licence provenance comments (visual-hashing has them) and `allow-wildcard-paths`.** `deny.toml:12` has the allow list, with no per-entry note on which crates need it. `deny.toml:21-22` has `multiple-versions = "deny"` and `wildcards = "deny"` with no skip list and no `allow-wildcard-paths`. lillith_memetics needed a long `skip` list and `allow-wildcard-paths = true` once it had a real graph (`syn`, `getrandom`, `hashbrown`, `thiserror`, `toml` families). The root package has zero dependencies, so this passes now. See section 4 for the forward consequence.

**F9 — LOW — CI action comment is imprecise.** The toolchain action SHA is annotated `# stable branch, 2026-03-27` (`ci.yaml:27` and following), where purrdf annotates the same SHA `# v1`. The SHA is identical, so there is no pin risk. Only the comment differs. There is no `.github/dependabot.yml` (gmeow-gts has one, and its history shows grouped action bumps), so pinned SHAs go stale with no update path. Add a monthly `github-actions` update config, or state in CONTRIBUTING who bumps them.

## 2. Doctrine fit (AGENTS.md / CLAUDE.md / plan decisions)

- **D1 — MEDIUM — "Rust first" versus the shell gates.** `AGENTS.md:138` says "Checks, generators, gates and tests are written in Rust ... Shell is limited to thin glue such as the Makefile and hooks". `Makefile:51-64` (`licenses`: sha256 compare plus text scraping of the backtranslation record) and `Makefile:66-75` (`issue-refs`: 10 regexes and exit-code arithmetic) are checks implemented as shell inside the Makefile, not glue. The plan chose the Makefile target (A12 and the `issue-refs` row), so this is not a deviation from the plan. It is a deviation from the repo's own stated rule. Either amend the wording ("until `raf-workplan` hosts them, two shell gates are the exception, with the Rust tests as the replacement") or move both into `tests/` as Rust checks that the Makefile only invokes. The wording fix is one sentence.
- **D2 — LOW — Every rule has a negative fixture.** The `docs_contract` rules do (the test has per-rule fixtures; the 46 tests run). The Makefile gates have only the manual throwaway-clone check recorded in validation.md; no committed fixture drives `make issue-refs` or `make licenses` to a failure. Same remedy as D1.
- Plan decisions are honoured: MSRV 1.98.1 appears consistently (Cargo.toml, Makefile, ci.yaml); `.goals`, `.baseline` and `.stage` are ignored and untracked; the census-porting freedom is stated nowhere in the repo; `.deficiencies` has the purrdf notice and marker with no entries. No attribution text was found in the new files.
- **D3 — LOW — CLAUDE.md "Never: add a `#![feature]`".** It is enforced only by the MSRV build (`AGENTS.md:62-64` says so). That is sound, because the msrv job is the guard. No change needed.

## 4. Consumers and blast radius

1. **`tests/docs_contract.rs` is the only executable gate over 21 capability documents, 21 change records, 2 architecture pages and the README.** It runs inside `cargo test --workspace` (`Makefile:25-26`, CI `test` job). It is std-only and uses a hand-written line-based frontmatter parser, so nested `bindings` structure is checked shallowly (plan, "declined" list). Everything that follows consumes the format it enforces:
   - `raf-okf` (the okf-profile capability; root of its dependency graph, with no dependencies) must accept exactly the documents this test accepts. Any key-set or section-order edit here is a contract change for it.
   - `raf-source` (`source-index`, also a root) is a transitive dependency of `workplan-document-model` -> `reconcile`, `generated-docs`, `evidence-claims`, `two-way-coverage`, `entity-history`.
   - The census chain: `census-normal-form` is the root of 7 of the 9 census capabilities (ledger, detectors, debt-ratchet, migration and, through them, patterns, rule-api, cli). `census-ledger` is the second-order hub (patterns, rule-api, reference-scan, cli, debt-ratchet, migration). `census-cli` depends on 4 others and has no dependents.
   - The workplan chain: `workplan-document-model` is the hub, with 6 direct dependents. `workplan-complete-gate` depends on `reconcile` and `generated-docs`. `workplan-prose-assessment` depends on both plus the gate. `workplan-cli` depends on gate, reconcile and generated-docs.
   - A wrong id or cycle here is caught by the test (acyclicity and id resolution are enforced), so the graph (21 nodes, no cycles, all targets present) is internally sound. A wrong dependency direction would not be caught. That is a review-time risk and the reason the five considered documents (`workplan-current-rationale`, `entity-history`, `evidence-claims`, `prose-assessment`, `two-way-coverage`) should not be promoted without re-reading their `depends`.
2. **README claims.** `README.md:26-31` links six crate rows to capability docs, each marked "designed — not yet published". These links are resolved by the test (relative links and anchors in the README are checked: see the `README.md` fixtures at test lines 1308, 1494-1510). `AGENTS.md:33-44` repeats the crate table, so a status change needs edits in both, and no check compares them. LOW drift risk. Change the count of the table's rows only with the capability docs.
3. **Crate-creation issues (the next work) inherit the gates.** Items that will fail on the first real crate:
   - `deny.toml` `multiple-versions = "deny"` plus `wildcards = "deny"` with no skip list (F8). The first crate that pulls `syn`, `clap` or `serde_yaml` will probably hit duplicate versions, as memetics did. The branch's own comment says additions "require someone to look". Expect the first crate PR to carry `deny.toml` changes, and `unicode-ident` (`Unicode-3.0`) to need an allow entry.
   - Licence texts in each crate directory: `cargo package` ships only the crate directory. gmeow-gts added `go/LICENSE-*` late and then had to add a recipient-archive check (b7f1d14); purrdf generates bundles (`license-bundles`). The root-only `make licenses` check will not notice a crate published without `LICENSE-MIT`/`-APACHE`/`-MULAN`. Per-crate `license-files` or copies, plus a check, belong with the first crate.
   - `Cargo.toml` `members = []` (line 20): `make msrv`, `clippy` and `test` use `--workspace`, which includes the root package, so they are non-vacuous today. When `crates/*` is added the root dogfood test must remain a member.
   - `src/lib.rs` is the root package and carries `missing_docs = "deny"`; the self-gate issue replaces `docs_contract.rs` with `raf_workplan::Gate` (plan). Until then, the Rust test and the Makefile `issue-refs` are two implementations (F2) and the swap must retire one of them.
4. **Release tooling.** `cliff.toml` (F1), `CHANGELOG.md`, `CITATION.cff` and the `v[0-9]*` tag pattern are consumed at the first tag. A wrong `cliff.toml` costs a rewritten changelog and a tag.
5. **Hosted CI is unverified.** Validation records PR 11 run 38210871728 as "NOT RUN" because of an organisation billing block, so every `ci.yaml` job (including the reuse and deny installs, and F3) has been checked only by `actionlint`, `shellcheck` and local equivalents. Treat any first green hosted run as new evidence: `cargo install cargo-deny` in particular has never run on a hosted runner for this repo.
