# Platform binding applicability

Read-only diagnosis; no product edits, builds or execution. The current blocker is genuine: Source binds two tests beneath `tree::disk::tests::windows`, whose enclosing module has `#[cfg(windows)]`. On Linux the existing list pass sees zero tests and correctly returns `NoTestListed`. Current TestFn exposes identity/package/target/name but no applicability evidence. The general zero-list refusal must remain.

The complete captured issue 23 explicitly allows a declared-platform or actual cfg-based applicability rule, requires a reported reason distinct from passing, applies it to every platform-specific binding, reconciles the completion contract, and requires real hosted verify on Linux/macOS/Windows. Those full acceptance obligations remain open. This repair can establish truthful native-host applicability for current completion without claiming those hosted results.

## Smallest coherent production direction

Add a narrow typed native-platform applicability observation through raf-source's existing parsed cfg facts and actual module/target context. Do not reparse Rust independently in Workplan, infer platform from a test/module name, or run a broad Cargo feature/config resolver. `facts.rs` already parses cfg/cfg_attr through `cfg::CfgExpr`; preserve the relevant effective guards alongside the source facts and propagate enclosing module/crate guards to each actual TestFn context. Own-function attributes alone miss both failing Windows tests. Inner crate/file guards and parent module declarations matter to the original platform-specific bindings too.

Evaluate only the known native platform atoms (`unix`, `windows`, supported `target_os`/`target_family`) under explicit executor platform input, with three-valued all/any/not composition. Other atoms remain Unknown, including features/custom cfg; do not invent their values. A definitely false effective platform guard produces `NotApplicable { platform, reason, source }`. True or Unknown continues through the existing list/run proof, so an unknown/feature-disabled test listing zero remains a refusal. A false branch in `all(windows, feature=...)` on Linux is sufficient; `any(windows, feature=...)` on Linux is not. `test` context can be modeled as test compilation, but a nonplatform condition alone is not grounds for a platform skip. Conditional cfg_attr application must retain its implication semantics or remain Unknown; never flatten it as an unconditional guard.

Platform inputs need an explicit native-host execution contract. The current commands use native libtest execution; do not quietly certify a different target chosen by Cargo config/environment as that host. If selected-target determination is necessary, obtain maintained compiler facts through the actual toolchain/runner; do not use string guesses or silently accept an unknown cross-target execution context. This is a bounded native applicability feature, not full dependency cfg evaluation from issue 48.

`bound::Plan`/`BoundOutcome` must represent this separately from Passed, Failed and Unresolved. `Evidence::passed()` must stay false for NotApplicable; do not fabricate one listed/passed test. Verify/completion may regard an explicitly justified host-inapplicable binding as satisfying this host's applicable obligations, but their reports must retain its path and reason and distinct executed/skipped counts. Existing `!evidence.passed()` loops in `lifecycle::{complete,verification,examples}` need explicit outcome matches, not a changed global definition of passed. Typed CLI/RDF output must preserve that distinction. `record_evidence --from-binding` cannot write a passing EvidenceRecord for a nonexecution: refuse actionably without publication unless its record schema is deliberately expanded with a distinct supported outcome.

Do not remove Windows bindings, gate tests behind another no-op wrapper, count a zero-test run as pass, or skip every unresolved binding. Keep claim owners and actual Windows proofs bound. A host-neutral conformance test is an alternative only if it runs real local assertions on every host and keeps separate native Windows evidence; merely wrapping a Windows body in `cfg` with an empty Linux body is not a repair.

## Focused patch and proof plan

1. Source observation/propagation: actual Windows-gated parent module test, Unix/Linux/macOS counterparts, crate-inner guard and same file reached through different target contexts. Test explicit platform inputs without changing global environment or claiming an unexecuted host run. Maintain original source/item/work grants and actionable read/storage errors.
2. Bound planning: known false Windows-on-Linux is typed NotApplicable with exact source reason and zero runner calls; matching Windows platform plans the real ordinary test. A matching-platform zero listing still gives NoTestListed. Unknown feature/custom cfg and `any(platform, unknown)` preserve refusal; contradictory unsupported inputs never silently pass.
3. Real native caller: use a fixture with an opposite-host gated test plus a runnable local neighbor and a genuinely missing/disabled-feature binding. Verify/completion must show one local proof and one justified inapplicable row, then refuse the missing/unknown case with no lifecycle write. This proves the rule rather than executing Windows on Linux.
4. Evidence/CLI projection: verify exit 0 for applicable proofs plus explicit inapplicability; distinct output counts; zero execution never becomes pass; --from-binding inapplicable request starts nothing and writes no record. Preserve existing zero-count, ignored, no_run, compile_fail and failure tests.
5. Current strict completion rerun with the two real Windows bindings retained, then normal adoption/default gates. Full all-platform verify acceptance remains owned by issue 23 until the actual three hosted runs pass.

This is more work than a two-name skip list, but it fixes the actual source-to-executor contract. The current implementation has no existing typed NotApplicable path to reuse, so there is no truthful metadata-only bypass for these zero listings.
