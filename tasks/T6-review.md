## Findings

### Blocking

1. **A 22-file input produces 4 million module-path records; the walk has no bound on them.** modtree.rs:`enter`/`load`/`body` and workspace.rs. Each arrival at an already-parsed file re-walks its children and pushes one `Reach` per module path, as C6 requires ("parsed once and indexed under every path"), so a chain of files that each declare the next twice (`#[path = "m1.rs"] mod a; #[path = "m1.rs"] mod b;`) doubles at every level. Probe, release build: n = 10 gives 4 095 reaches in 3 ms; n = 16 gives 262 143 in 0.19 s; n = 20 (22 files, about 1.3 KB of input) gives 4 194 303 in 2.7 s. n = 30 needs roughly 10^9 records and does not finish. `Budget::ModuleDepth` (128) does not help, since each level is only one deep. A repository whose gates read untrusted trees and whose Bounds text says memory exhaustion is made unlikely should not be killable by a crafted tiny tree; the same crate already added a walk-level budget for depth, so a walk-level budget for visits or recorded reaches belongs here. Fix: add a typed budget (for example total module visits per load, or reaches per file) that fails with `Budget{..}` naming the file and declaring line, state it in the Contract Resource bounds paragraph and SECURITY.md Bounds, and add a refused fixture beside an accepted diamond (n = 4). The "indexed under every path" semantics stay for every realistic input.

2. **Two targets with one crate path load silently.** target.rs `derive_targets` (only equal roots are refused). Probe, MemoryTree: two explicit `[[test]] name = "a"` tables with different paths load and give two targets both `demo::test_crate::a`; `tests/a-b.rs` and `tests/a_b.rs` give two targets both `demo::test_crate::a_b`. Cargo rejects the first. The Task 7 index keys items by crate path and merges equal path, namespace and kind into one symbol with several sites (C7, cfg twins), so items of two different targets would be merged as if they were cfg twins, with no error. Fix: a `TargetProblem::DuplicateCratePath { crate_path, other }` error naming the second target's manifest key, with a refused fixture beside the distinct-name neighbour. The same gap is why the Task 6 list item "`test_crate` collision" has no fixture: there is no test of a first-party `mod test_crate;` beside a test target, whose two files must both load under `demo::test_crate` and `demo::test_crate::it` (the ambiguity itself is Task 7's, but the load-level fixture belongs to this task).

   - DiskTree "link to a symlink that itself points outside the root" (source-index Verification, which "## Task 6" says to run in full through `Workspace::load`): tests/workspace_containment.rs has the direct outside link, the `vendored/..` case, the manifest targets, the loop, the FIFOs and the in-root link, but no chained outside link. The code path is the same `contain`, so the risk is low and the fixture is five lines.

### Non-blocking

4. **Build script (adjudication 1): the name is not a deviation; the shipping flag is a policy choice that needs a decision recorded.** target.rs `build_script`: `name = "build-script-build"` is Cargo's own name for the target and the plan defines `Target.name` as the Cargo target name; `crate_path = <pkg>::build_script` matches C5 and the completeness row. The plan says only that `shipping` is "derived from `kind`", and does not state the value for a build script (the earlier analysis recommended `true`, the document and tests now say `false`; I found no plan text that requires `true`). So `false` is not a required deviation. It does have a consequence the documents have not absorbed: docs/capabilities/census-detectors.md:49-53 says the census "walks shipping code and every test, bench and example target", and a non-shipping build script is none of those, so `build.rs` is invisible to the census as written. Either set `shipping = true` for `BuildScript` (the filter `!t.shipping` in the Usage block would then stop lumping it with tests) or make the census text name the build script. Decide in Task 9 at the latest.

5. **Symlink classification in discovery (adjudication 2): containment holds; the diagnostics are partly wrong.** discovery.rs:`symlink` calls `tree.read(path, 0)`. `DiskTree::read` runs `contain` (canonicalise and prefix check) before it opens anything, so a link leaving the root fails with `OutsideRoot` without an open; a link to an in-root FIFO or device is opened `O_NONBLOCK|O_NOFOLLOW`, `fstat`-ed and refused `NotRegular` without a read; a link to a regular file reads at most one byte (`take(1)`) and then returns `TooLarge` (or `Ok` when empty), which the walk treats as "a file", and `TooLarge` is decided before UTF-8 so a binary file never turns into `NotUtf8`. Every outcome is an `Ok` or a typed error; nothing becomes absence. `entry`/`list` cannot answer the question (they report `Symlink` without following), so a `read` probe is the available mechanism. Probe results (DiskTree): a link to an outside file fails the whole load with `leads outside the root`; a dangling link fails with `no such file or directory`; a link to an in-root FIFO fails with `a symlinked directory is not followed`. Problems: (a) the FIFO case is mislabelled `DirSymlink` because `NotRegular` is read as "directory"; (b) source-index.md line 158 says "a symlink to a file is left alone", which is not true for an outside-root, dangling or special-file target (they are hard errors, which is acceptable under fail-hard, but the text should say so). Fix the text, and either map `NotRegular` to a `NotRegular` tree error for non-directories (not possible with the current API) or word the `DirSymlink` message as "a symlink that is not a regular file".

6. **ModuleDepth (adjudication 3): justified and consistent.** The walk recurses on the caller's thread (2 MiB in tests), so an unbounded chain is a stack overflow, which C3 forbids; "no rule of its own" is about the OKF profile, and this is a resource bound with a typed `Budget` error naming file, line and module, documented in the Contract (source-index.md:123 and :205) and in the `Budget` table. Two small gaps: the Constraints bullet (source-index.md:272) and SECURITY.md Bounds still list five budgets, and the depth bound is counted per path, not per load (finding 1).

7. **Dependencies (adjudication 4): justified.** `quote` (default features off) provides `ToTokens` for the attribute arguments, visibility and impl header text in facts.rs; syn `printing` is its prerequisite and both are already in syn's graph, so no new crate arrives. `toml` is used with `std`, `parse`, `serde` and no `unbounded`; the 1000-level fixture passes on the 2 MiB test thread. The lockfile adds only the toml/serde family. `make deny` and MSRV were reported clean by the orchestrator and implementer; I did not re-run them.

8. **Nested `cfg_attr` and `cfg_attr(.., cfg(test))` are silently ignored.** facts.rs:summarize handles `cfg_attr` only for a direct `path = ".."` operand; `#[cfg_attr(a, cfg_attr(b, path = "x.rs"))]` and `#[cfg_attr(test, cfg(test))]` fall through the `_ => {}` arm (facts.rs:436, and the inner loop's implicit skip), so a path site can be missed when a default file exists, and a test tag can be missed. The comment on the arm should say what is deliberately not modelled, and a nested `cfg_attr` should either be expanded or be an error.

9. **Consumer shape for Task 7 (adjudication 9): sufficient, with four small additions.** `FileFacts`/`ModBody` give `ItemFact { name, kind, name_line, span (lines and bytes), body, vis, attrs, documented, doc_hidden, test, macro_export, members }`, `ModFact` (with `paths`, `inline`, `test`), `UseFact { tree, leading_colon, vis, test }` with renames/globs/groups, `extern crate x as y` (`renamed_from`) and `ImplFact { trait_path, self_type, self_path, items }`; `SourceFile.reached` carries target, module path, test flag and predicate; identity `(file, span.start_byte)` is available.
