# Exact locked source authority design

Read-only source-backed proposal, not implemented or executed acceptance. Current plan and package identity reviews were read. Repository memory supplies no standing authority for a source backend; Graphify remains unavailable. No builds, product edits, upstream changes or service operations were performed.

## Smallest coherent boundary

Preferred after clarifying the raw-object seam: an immutable verified Git-object Tree is simpler than authenticating a live supplied text Tree, provided it consumes caller-supplied bounded raw objects rather than implementing a host object database. The catalog can still admit independently rooted path Trees with explicitly different evidence. Do not widen DiskTree's root, use Cargo JSON, or make the source library discover a host Git checkout/cache automatically. The live-Tree verification option below remains viable but is not required.

The public catalog needs three distinct concepts, with constructors validating before publication:

1. A load-local authority handle and one independently rooted `&dyn Tree` supplying candidate text. Neither caller labels nor FileIds prove content.
2. An exact locked source key: Git URL/source fields plus full precise revision, and the admitted package manifest path within that source. Keep this separate from package name/version and from the physical Tree locator. Do not use cargo-lock SourceId wildcard-like equality as the exact key.
3. A checked Git snapshot witness binding the selected commit to its root tree and each permitted directory/path/mode/blob. The checked descriptor is opaque: callers cannot fabricate a boolean `verified` flag. Package metadata and source bytes are read through this descriptor before exact dependency roots are published.

An input builder can consume raw commit/tree/blob object payloads supplied by a caller and retain checked object/path records under native admission. It need not fetch, spawn Git, read `.git`, decompress packs or implement another object database. The real caller can obtain those bytes from its existing pinned Git store; the library still verifies their binding itself. Missing objects or incomplete required evidence refuse. This is a Git source authority, not registry archive support: unsupported registry/patch/replacement sources cannot silently become grounded providers.

## Exact verification operations

`Tree` currently exposes UTF-8 `read`, same-open `read_unseen`, identity, sorted directory `list`, and `entry`. It cannot carry arbitrary binary Git tree objects. Keep bounded raw object witnesses outside that trait rather than pretending tree objects are UTF-8 source files.

The selected pin supplies `purrdf_hash::sha1::Sha1::{new,update,finalize,digest}` and public `OUTPUT_LEN = 20` (verified with `git show` at `5db00aaae9f3abb521e98b8f79dbc1bebe5e3e43`). Reuse it for the actual Git object identifier: hash object type, space, decimal payload byte length, NUL and exact payload bytes. A raw payload SHA-1 alone is wrong. Retain hash algorithm as part of the source profile; reject unsupported object formats instead of truncating or guessing.

Validate the locked commit object's identifier, require its actual tree header, then verify each required tree object by its parent reference. Use maintained `gix-object` binary decoding instead of writing a Git object parser: see the concrete dependency seam below. Apply RAF authority policy to decoded modes/names/object IDs. Reject ambiguous/duplicate or unsupported path spellings before normalization, malformed records, missing ancestors and unsupported symlink/gitlink traversal. Commit parent objects need not be traversed to establish this snapshot's root. No compatible public PurRDF Git object decoder was found; the decoder dependency does not replace the native hash.

For each source file returned by the supplied Tree, hash exactly the returned String's UTF-8 bytes as a Git blob and compare the witnessed blob. This verifies LF/CRLF and edited text; do not normalize, reconstruct from syn, trust HEAD, trust `.cargo_vcs_info.json`, trust version strings or rely on `git status`. Manifest text, inherited workspace metadata and every module/target path must pass the same boundary. Authenticated Cargo.toml still has to agree with the selected lock package/edge identity; the hash does not establish that agreement by itself.

The descriptor's verified directory entries must govern discovery, target probing and absence, not just eventual `.rs` reads. A useful minimal adapter presents the exact committed tree: `list`/`entry` come from checked Git entries, and only witnessed regular files are fetched from the candidate Tree. Untracked checkout files are consequently outside this snapshot rather than silently influencing discovery. State this semantics explicitly. Comparing complete physical listings is an alternative dirty-checkout policy, but is unnecessary for a committed-snapshot view. Partial manifests that can omit a target/module are not adequate evidence.

Do not let backend `Opened::Seen` bypass verification. Before a first verified read, force access to the actual candidate text and verify it. Only a checked, retained snapshot record may subsequently answer Seen. A backend identity or a previous read from another authority is insufficient. Preserve existing per-file limits before candidate reads; admit witness objects, retained descriptors, file text and verification work before allocation/processing through the original grants. Caller-owned already allocated witness input is not a claim of RAF preallocation control.

## Integration holes to close

- `Workspace::load_with` presently threads one Tree through discovery, target derivation, Reader/package metadata and Walker. Walker keys `spellings` by RelPath and `by_id`/active cycles by FileId; Workspace files and visits also use RelPath. Add authority to physical path/cache/identity keys throughout, including manifest caches and reachability caches. Equal `src/lib.rs` or MemoryTree file keys in two authorities must not merge.
- `RelPath::join` preserves `..` for backend interpretation. A composite virtual prefix alone is unsafe: `authority-a/../authority-b/file.rs` can cross the dispatch boundary while remaining below the composite root. Perform joins within the selected authority's own RelPath root, then pair with authority; never dispatch a joined path by its first textual segment. Keep DiskTree handle containment unchanged.
- Give targets/packages/files explicit authority-qualified locations. Keep display crate/item names and first-party RelPaths unchanged where their existing APIs promise them; provide qualified source access instead of inventing versioned Rust paths or projecting two physical files onto one public map key. Dependency edges, not Rust module traversal, are the only permitted authority transition.
- A shared repository authority is appropriate for PurRDF's sibling path dependencies and workspace inheritance: its committed root must cover the actual workspace, with a selected package manifest beneath it. Do not root each crate at its own directory and then silently permit escapes to siblings. A source crossing to another admitted authority still requires an exact declared/locked edge.
- Preserve parse sharing within one actual authority/source, but distinct target/test/edition semantic contexts. Defining-trait identity and package-qualified queries remain necessary; verified bytes do not fix displayed-trait-key collisions or evaluate cfg/macros.
- Native Memory/WorkList/OrderedTable are available for checked witness/frontier storage; no fake provider calls or parallel resolver are needed. Native hash must be a real dependency of the verification production caller, not a test-only import. Return typed actionable stale/missing/ambiguous/source-verification and original Budget/Storage failures before publishing a grounded root.

## Why not a host Git object Tree first

An immutable Git-object-backed Tree serves authenticated source bytes directly and avoids checking a mutable checkout. It still needs modes, directory completeness, identity scoping, raw byte limits and checked commit/tree binding. Implementing host repository access would introduce object format, loose/packed objects, alternates, replacement objects, promisor fetch/network behavior and subprocess/resource policies. Existing Tree supplies none of those host operations. A caller-supplied raw-object seam avoids that extra host surface while exercising the same production walker and native content hash. Do not call a raw Git command's output an authenticated object without checking its exact object bytes.

Clarification: the preceding host-ODB concerns do not apply to a Git Tree over a raw-object supplier. That is the recommended minimal implementation. Its public object seam returns bounded `(kind, raw body)` for a requested exact object ID; no host path, Git command, fetch or pack reader is part of RAF. The Git Tree hashes that exact body with the returned kind and length before decoding/using it. The commit/root/tree path verification above then authenticates both complete directory results and the actual blob text. Convert verified blob bytes to UTF-8 text without text normalization. This removes checkout mutation, untracked-file and backend-Seen races instead of adding checks around them.

Use authority plus snapshot plus file path for FileId, not blob ID alone: two different files with identical contents can have different relative module contexts and must not be mistaken for one physical file. `read_unseen` may skip returning a verified file's text, but must not invent an unverified authority record. The raw supplier must receive the explicit maximum before acquisition; validate actual returned length too. Native admission covers RAF-retained buffers/decoded records, and work charges hashing/decoding/path visits. A generic third-party supplier's prior allocations are its responsibility; do not claim that receiving a Vec retrospectively admitted its allocation. Missing/wrong-kind/hash-mismatched objects refuse, never fall back to the live checkout.

Thus the smallest coherent path is: bounded raw object supplier, native hash binding, maintained borrowed Git decoder, independently rooted immutable Tree, authority-qualified catalog/walker, exact locked edge selection, real pinned PurRDF query. Ordinary path fixtures use their supplied Tree and never gain Git-verified status from a label. The actual pinned native objects and refusal neighbors remain mandatory execution; none were run in this review.

## Maintained binary decoder seam

Official [gix-object 0.64.1 API documentation](https://docs.rs/gix-object/0.64.1/gix_object/) supplies borrowed CommitRef, CommitRefIter and TreeRefIter. Prefer fallible token iteration where it avoids allocating parent/header arrays; exhaust required validation and propagate every decode error. This is a decoder-only dependency, not a reason to add full gix repository, object-database, transport, signature or subprocess features. The [CommitRef API](https://docs.rs/gix-object/0.64.1/gix_object/struct.CommitRef.html) accepts the object hash kind explicitly. Native SHA1/hex still verify the object framing and expected ID.

Current [upstream tree iterator source](https://github.com/GitoxideLabs/gitoxide/blob/main/gix-object/src/tree/ref_iter.rs) contains a concrete unsuitable convenience: `next_entry` filters away decoder errors before finding a name; its lookup helpers reuse that behavior. Do not use these helpers for an authority proof. Consume raw TreeRefIter results with `?`, validate the complete directory, then select its entry. Inspect the selected release's exact implementation before finalizing this caller.

Current [upstream manifest](https://github.com/GitoxideLabs/gitoxide/blob/main/gix-object/Cargo.toml) identifies a small object crate with optional signature/serde and separate hash features, but its version is 0.66.0, whereas the observed published API documentation is 0.64.1. This review does not claim a locked dependency closure, selected feature graph, licensing gate or allocation guarantee for either version. Resolve and inspect one exact supported release before implementation. Borrowed iterators reduce allocation; they do not admit the raw input or retained catalog. Apply the original limits around both.

Unicode filenames remain exact UTF-8; invalid UTF-8 names must refuse when a directory is exposed, matching Tree's no-dropped-entry law. Preserve Symlink entry kind where listing can represent it, but refuse traversal in the initial checked-snapshot profile; do not reinterpret a Git symlink blob as regular Rust text. `entry` absence and `list` membership derive from the complete verified tree, and `read` preserves max bytes, regular-file and UTF-8 errors. No generic decoder convenience may convert malformed object data into an absent file.

## Required real neighbors

Use actual pinned PurRDF manifest and symbol bytes, exact lock URL/revision and real alias/reexport routes. Require matching native symbol resolution and distinct wrong-revision/edited-byte refusal before claiming preferred-provider grounding. Add: wrong commit/tree/blob linkage; omission/addition of target entries; altered manifest with same name/version; symlink/gitlink path refusal; LF/CRLF distinction; a backend returning Seen for unverified text; equal path/FileId across authorities; `..` crossing with an inside-authority sibling valid neighbor; two locked versions/sources and wrong-source same-name symbols; exact/one-less original work/storage/file limits. Verify missing metadata does not become an unknown extern success.

The proof is equality with the selected Git snapshot under Git's object-identity assumptions, not a signature or proof that a URL owner authored those bytes. The trusted lock/source selection remains an explicit input. This proposal does not complete feature/cfg, macro, standard-library, registry archive or preferred-provider enforcement policy.
