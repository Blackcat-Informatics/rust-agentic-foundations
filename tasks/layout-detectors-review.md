# Byte-layout adapter source review

Read-only review of `detectors/{mod,layout}.rs`, `gate/{rules,evaluate}.rs`, the physical owner index, Source `item_at`, and the new five-case Gate fixture. No builds or tests run. This does not assess completion of the fourteen-detector capability.

## Concrete findings

1. **Alignment rounding overmatches alignment down.** `is_rounded` accepts any simple local path without binding evidence. Consequently `fn copy(n: usize) -> usize { n & !7 }` is reported as rounding up, although it only clears low bits. Preserve `(n + 7) & !7` as a positive; make the direct-mask expression a negative. A local should qualify only with an actual biased-add definition, respecting shadowing/reassignment, or the matcher should conservatively require the expression itself.

2. **Mismatch evidence is unrelated within a function.** `function` emits every stored word-load XOR when any zero-count call occurs anywhere in the body. For example `fn copy(a: &[u8; 8], b: &[u8; 8]) -> u64 { let _unrelated = 1u64.trailing_zeros(); u64::from_le_bytes(*a) ^ u64::from_le_bytes(*b) }` is a checksum, not a first-mismatch index, but is reported. Require a zero count on the XOR result (directly or through a justified local); preserve the current direct XOR/zero-count positive and add the unrelated-call negative. Closures and shadowed load-local names also currently share the enclosing frame's evidence.

3. **Formatting does not prove a length prefix.** `visit_macro` only checks that a place and its length occur among arguments. `fn copy(b: &str) -> String { format!("{}:{}", b, b.len()) }` is reported even though the length follows the data. The matcher also ignores format placeholder selection. Restrict this path to an actually understood length-before-data format, or leave unsupported formatting unreported. Keep the real binary write-prefix positive.

4. **One numeric caller bypasses the shared native decoder.** `is_low_mask_complement` still uses `LitInt::base10_parse::<u128>()`, while `is_one` already uses `normalize::parse_integer`. Reuse that same established decoder here, preserving supported Rust literal spellings and overflow refusal. This is a narrow native-preference correction, not a request for another parser.

## Focused repair recheck

Re-read only the four findings against the current repair. The original direct-mask false positive is closed: alignment now compares actual add bias with the complemented mask. Mask literal decoding now uses the established native adapter and checked increment. The original unrelated-zero-count false positive is closed: the count receiver must retain an actual word-load XOR. The original reversed-format case is closed by rendered placeholder selection, including explicit positional/named selectors and escaped opening braces. Local shadowing and ordinary assignment now invalidate tracked XOR/load evidence.

Two concrete residual cases remain in those repaired paths:

- Compound assignments are `ExprBinary` with an assignment `BinOp`, not `ExprAssign`. `fn copy(a: &[u8; 8], b: &[u8; 8]) -> u32 { let mut x = u64::from_le_bytes(*a) ^ u64::from_le_bytes(*b); x &= 0; x.trailing_zeros() }` retains the old XOR association and is still reported. Invalidate a tracked destination for every compound assignment, preserving the direct XOR-count positive.
- Rust `.*` precision consumes an implicit argument before selecting the value. `fn copy(b: &str) -> String { format!("{:.*}{}", b.len(), b, b) }` renders `b` twice and never renders the length. `first_pair` instead selects the precision expression as the first rendered value and reports a length prefix. Conservatively leave unsupported consuming format specifications unmatched, or account for that real argument consumption; keep ordinary ordered fields as a positive.

These are source-derived counterexamples, not executed claims. Parent reported the focused Gate methods passed before its final assignment/home-report correction; no runtime was run by this reviewer. No new ownership/package defect was identified in this recheck, and no full capability acceptance is implied.

## Default-hasher adapter review

Three concrete source-derived findings in the new adapter:

1. **Non-unit type positions have no report owner.** `struct Cache { map: std::collections::HashMap<u8, u8> }` is recognized by visit_type_path. Source item_at selects the containing Struct; Census Owners contains no Struct/Type units. The actual builtin_hits path therefore refuses with “detector hit must have one physical census owner”, rather than yielding a detector finding. A standalone `type Cache = std::collections::HashMap<u8, u8>;` has the same mismatch. Decide and implement the real owner/report boundary without silently pretending those source items are existing Census units. The present fixture only covers function-owned type positions.

2. **Generic type parameters do not shadow imports.** `use std::collections::HashMap; fn copy<HashMap>(_: HashMap) {}` is a valid generic function, but Names still maps its type parameter to the imported standard collection and reports it. Scope entry must account for actual type-parameter bindings (including impl/trait contexts), preserving the ordinary imported-collection positive.

3. **Visible alias chains expand only once.** `use std::collections as c; use c::HashMap as Map; fn copy(_: Map<u8,u8>) {}` is missed: Map expands to c::HashMap and required does not resolve c. Resolve this bounded lexical chain with cycle/unknown handling, or state its unsupported limit explicitly; do not introduce another symbol resolver. A direct std import remains the positive control.

No further concrete defect found in direct annotation inference: only a recognized standard collection with sufficient generic type arguments vouches for its immediate constructor expression; arbitrary Map/Set suffixes do not. Wrapped nested constructors remain independently visited. Module import state is reset rather than inherited; block state restores after traversal; bare unimported names are not assumed standard. The existing all-target metadata applies to this detector and physical findings still flow through the common home-package path. These are source judgments only; no build/runtime or complete-detector acceptance is claimed.
